# 从结构证据建立项目理解

本规范参考 [Understand Anything 固定版本](https://github.com/Egonex-AI/Understand-Anything/tree/4e6d3299017a7432da15957874992837a315c5b4) 的扫描、importMap、neighborMap、架构分析与 tour 流程。本 Skill 独立实现 Python 有限范围的结构支持，不依赖该外部项目；本文已包含执行所需的规则。

## 先看仓库关系，再写局部正文

architecture 返回 repository-context.json：内部导入候选、反向引用、顶层定义、未解析的调用位置、目录分组、入口语法线索和有源码行数上限的关联批次。目录分组不等于架构，出现调用表达式也不等于目标已解析。

根据入口、声明依赖和导入邻域组织阅读。每个候选模块至少回答：对外承担什么职责，输入输出是什么，持有什么状态，调用与被调用方是谁，配置/数据/外部服务怎样影响它。阅读候选邻居的具体实现，不能凭符号名称补写业务意图。

Python 模块解析仅提供根目录与常见 src 布局的候选。多候选、运行时路径修改、插件注册、重导出和动态加载需要继续查证。工具明确标为 external_or_unresolved 时，不可直接宣称它是第三方库；可能只是搜索路径尚未解析。

## 保存可复核的架构认识

在 project.architecture 的正文中明确模块职责和依赖方向，并说明划分依据；project.flows 从真实入口描述跨模块行为、输入变化、分支和输出，不把导入图当执行流程。同时按 [semantic-model.md](semantic-model.md) 填写 model.json 的组件、关系、状态、契约、执行路线及行为问题。

至少核实一条跨文件正常路径和相应异常路径。配置或共享状态另行追踪，不能从 import 关系推出数据流。分析完局部后回查架构和流程是否仍成立，不能分别写几段互不关联的介绍。

阅读顺序应说明从入口如何进入各核心处理过程；跨文件邻域补上下文，不要求用户回源码。最终将这些关系转写为自然语言正文和内部链接。

## 当前工具边界

语义架构、调用目标、数据来源、状态写入与依赖行为由 Agent 阅读实际实现后确定。工具检查模型文件归属、关系和状态引用、流程依据、行为问题及复核指纹的一致性，不自动推断或证明这些解释真实。

Python Notebook 入口参与导入邻域分析，但架构图中的行号是拼接视图；精确来源使用带 cell 的 units 和 chunks。大文件的关联批次仍可能超长，实际逐段阅读使用 analysis-chunks 的有界片段，并携带所在定义和跨文件邻域。不要把分块切口视为函数或业务的结束。
